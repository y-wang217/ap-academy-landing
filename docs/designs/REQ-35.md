# REQ-35: Durable Notion exports, an outbox with retry, idempotency and visible failures

Copied from the approved design on the Notion card (Feedback 7, approved after revise 2 of 2). The full design, with its revision history, test plan table and UI sketch, is on the card.

## Build notes (differences from the design, decided at build time)
- **Migration number.** The design says 0019 by default or the next free number. 0019 and 0020 are on `main`, so the file is `supabase/migrations/0021_notion_outbox.sql`, shipped first in its own PR (`req/REQ-35-migration`).
- **ADR number.** 0050 to 0052 are taken, so the ADR is `apps/tracker/docs/decisions/0053-notion-export-outbox.md`.
- **Permission matrix.** `supabase/tests/permission_matrix.sql` fails for any tracker table it does not classify (REQ-32), so the migration PR adds the `notion_outbox` rows and the three new functions there and in `apps/tracker/docs/permission-matrix.md`.
- **AC13 not built.** Decision 6: REQ-33's setup page is not on `main` at build time, so the "Notion exports" setup row is skipped. A follow-up card can add it once REQ-33 lands.
- **Retry now.** The UI sketch shows "[Retry now]" on a waiting row, and the e2e row presses Retry on a row left pending by a 500. AC12 listed only failed and uncertain rows as retryable, so `retry_notion_outbox` also accepts a `pending` row and makes it due now. Running, done and superseded rows are still 409 `not_retryable`.
- **Retry answers how the send ended.** `POST /exports/retry` answers `{ id, status, supersededBy }` with `status` one of `pending`, `done`, `failed`, `uncertain` (after the drain), not always `pending`, so the notice can say whether the retry worked.
- **A delivery that fails while a newer change is pending** is superseded by that pending row instead of going back to pending, so the one-pending-row index always holds. The expired-lease summary case does the same inside `claim_notion_outbox`.
- **A `schedule_summaries` insert** enqueues the org's daily task as well as the summary (AC1 says any of these inserts writes both).
- **Owner-only drain.** `withBackgroundDrain` captures the request's Supabase client, and the drain runs in `after()` with that client, so RLS still applies.
- **The import run** also delivers through the outbox when it is wired in (adoption enqueues the summary), so `sync_state` is written only by delivery (AC15).
- **Without an outbox** (unit tests with no database), the handlers call Notion directly as before REQ-35.

---

**Summary:** Every class save now records the Notion exports it owes (the student's Weekly Schedule and today's teacher-texts task) in a `tracker.notion_outbox` row written by a database trigger in the same transaction, then tries them once right away; anything not delivered is retried with backoff by later owner requests and the hourly run, never duplicated, and shown to Charlie with a Retry until it is done.

**Risk:** Medium. A new owner-only table behind the existing `is_org_owner` RLS pattern and definer functions that only insert into it after an explicit owner check. Notion already receives exactly this data today, so no new destination; no permission or auth change; no existing row is deleted or rewritten. The feature PR still carries `needs-human-merge` because it touches `apps/tracker/lib/notion/`, `app/api/scheduler/daily-task/` and `supabase/`.

## Problem
For Charlie (org owner). Today a class save and its Notion exports are separate steps in one request (`handleCreateClass`, `handleEditOccurrence`, `handleCancelOccurrence` in `apps/tracker/lib/scheduler/schedule-handlers.ts` call `syncStudents` and `refreshToday` after the store write). If the function dies, times out or Notion errors between them, the export is stale and nothing records that it is owed. Only `schedule_summaries.sync_state = 'failed'` remembers a summary failure, and only when the code got far enough to write it; today's task remembers nothing per save. A blind retry of a Notion append can duplicate a to-do because Notion may commit and still report an error.

## Acceptance criteria
- [ ] AC1: Any insert, update or delete on `tracker.class_series` or `tracker.class_exceptions`, and any insert on `tracker.schedule_summaries`, writes outbox rows in the same transaction: one `summary` row for each affected adopted student (old and new `notion_student_id` when it changes) and one `daily_task` row for the org. This holds for every owner write (the only role with class write grants, 0010), for `service_role` writes including deletes, and for writes through `split_class_series()`, `adopt_student_schedule()` and REQ-30's `schedule_write()`. A statement that fails or changes nothing (constraint, RLS refusal, stale `updated_at` match of zero rows, `split_class_series` raising `stale`) leaves no outbox row.
- [ ] AC2: At most one `pending` row exists per `(org_id, dedupe_key)`. A second change while one is pending updates that row (new `request_id`, `requested_at`, `version + 1`, `next_attempt_at = now()`) instead of adding a row.
- [ ] AC3: Delivery always renders the target from the current database state, never from a stored payload. A row is claimed only when no other row for the same `dedupe_key` is `running` with a live lease, so an older delivery can never land after a newer one. When a delivery for a target finishes `done`, every older `failed` or `uncertain` row for that target becomes `superseded` with `superseded_by` set.
- [ ] AC4: Backoff: after a retryable failure (network error, timeout, Notion 429 or 5xx) `next_attempt_at = now() + min(30s * 2^(attempts-1), 1h)`, or Notion's `Retry-After` when that is longer. After 8 attempts, or on a non-retryable error (Notion 400, 401, 403, 404, render error), the row is `failed`. A daily-task `busy` result (the daily task lease is held) reschedules 30s later without counting an attempt.
- [ ] AC5: Rate: one drain makes deliveries one at a time, waits at least 350 ms between deliveries, stops after 10 rows or 20 s, and stops at the first 429.
- [ ] AC6: Summary idempotency: every summary delivery reads the student's current Notion Weekly Schedule first and writes nothing when it already equals the rendered text, then marks the row `done` (the existing read-before-write in `syncStudentSummary`). A 500 then a success writes once; a timeout where Notion committed writes nothing more on the next attempt and ends `done`.
- [ ] AC7: Daily-task uncertainty: when a non-idempotent Notion call in `ensureDailyTask` (`append` a to-do, `createLog`) fails with a network error, timeout or 5xx, the result is `uncertain`, the outbox row becomes `uncertain`, and it is never retried automatically. A `running` daily-task row whose lease expired is also set `uncertain` when found, never re-run.
- [ ] AC8: First delivery: after a successful class save the handler looks up the pending rows for the keys that save touched with `findPending(orgId, keys)` (max 3: up to two students plus today's task), drains only those ids before responding, and the response carries `summarySync` (`synced`, `failed`, `skipped`, or new `queued`), `dailyTask` (`updated`, `unchanged`, `skipped`, `failed`, or new `queued` and `uncertain`) and `exports: [{ id, kind, status }]`. Class saves are owner-only today (`gate(deps, ["admin"])`), so a save always finds its own rows; if `findPending` returns none (a race with a concurrent drain that already claimed them), the response reports `queued` and the next drain delivers it.
- [ ] AC9: Background drain: whenever `realDeps().identity` resolves to an admin identity, `withBackgroundDrain` schedules exactly one drain of due rows for that org with `after()`, which runs once the response is sent. It never schedules for teacher, none, signed-out or unconfigured identities, and resolving the identity more than once in a request still schedules one. `POST /api/scheduler/daily-task/run` drains due rows for `DAILY_TASK_ORG_ID` on every authorised call, before and independent of the "not yet 06:00" check. A save whose function died after commit is delivered by the next of these.
- [ ] AC10: Save notice (REQ-28 builder in `apps/tracker/lib/view/save-notice.ts`): `queued` reads "Weekly Schedule for Ada L.: Queued. It will be sent shortly." and "Today's Notion task: Queued. It will be updated shortly." with tone ok; `uncertain` reads "Today's Notion task may have been updated. Check it in Notion, then retry." with tone warn and a Retry.
- [ ] AC11: Week editor: a "Notion exports" strip lists every outbox row for the org that is `failed`, `uncertain`, or `pending`/`running` and older than 10 minutes ("stale"), one line per student (by name) plus one line for today's task, each with its state, last error and a Retry button. It is hidden when there are none. A `failed` or `uncertain` row stays listed until a Retry or a later delivery for the same target supersedes it; nothing deletes outbox rows.
- [ ] AC12: `POST /api/scheduler/exports/retry` `{ id }` (owner only) calls `tracker.retry_notion_outbox(id)`. For a `failed` or `uncertain` row with no `pending` row on the same `dedupe_key`, that row goes back to `pending` with `next_attempt_at = now()`. When a `pending` row already exists for that key, the retried row becomes `superseded` with `superseded_by` = the pending row, the pending row gets `next_attempt_at = now()`, and the pending row's id is returned. The route drains the returned id and answers 200 `{ id, status, supersededBy }` (`supersededBy` is the original id in the second case, else null). A row in any other state returns 409 `not_retryable`; an id not visible to the caller returns 404 `not_found`. Teachers, parents and students get the guard's denial.
- [ ] AC13: Setup page (REQ-33, `/tracker/scheduler/setup`): a row "Notion exports" shows Done when no row is `failed`, `uncertain` or stale, otherwise Partial with "N failed, N uncertain, N waiting" and a link to `/schedule`.
- [ ] AC14: RLS: an org owner can select outbox rows of their own org and update only the status columns (`status`, `attempts`, `next_attempt_at`, `lease_until`, `last_error`, `payload_hash`, `superseded_by`, `finished_at`); an update of `org_id`, `kind`, `target_id`, `dedupe_key`, `request_id` or `version` is refused. Teachers, parents, students, another org's owner and `anon` can select, insert, update and delete nothing. No role but `service_role` has insert or delete; rows are created only by the definer functions, which check ownership or run as the trigger.
- [ ] AC15: `schedule_summaries.sync_state`, `last_error`, `last_written_text` and `last_drift_text` are still written, but only by the outbox delivery, so the Schedules page and REQ-33 keep reading them. No column is dropped.

## Approach (as approved, in short)
- Enqueue in the database with an `after` row trigger; deliver in the app; no stored payload, `payload_hash` per delivery.
- New: `lib/scheduler/outbox.ts` (policy and drain), `outbox-store.ts` (port), `lib/data/outbox.ts` (Supabase, Zod), `outbox-drain.ts` (`withBackgroundDrain`), `exports-handlers.ts` and the `exports` and `exports/retry` routes, `lib/view/exports-text.ts`, `components/scheduler/exports-strip.tsx`, the ADR.
- Changed: `deps.ts` (the one AC9 hook point), `schedule-handlers.ts` (`deliverOwed` replaces `syncStudents` and `refreshToday`), `summary-sync.ts` (returns the payload hash), `daily-task.ts` (`uncertain`), `daily-task/run` (drains first), `import-handlers.ts` ("Sync all" through `enqueue_summary_sync`), `lib/notion/*` (`retryAfterSeconds`), `schemas.ts`, `save-notice.ts`, `week-editor.tsx`, `e2e/tracker/mock-notion.mjs` and `flows.mjs`, the ops guide and PLAN.

## Migration
`tracker.notion_outbox` with the partial unique index on `(org_id, dedupe_key) where status = 'pending'`; `upsert_notion_outbox` (definer, no client execute), `enqueue_notion_exports` (trigger), `enqueue_summary_sync` (definer, owner check), `claim_notion_outbox` and `retry_notion_outbox` (invoker); owner select and a column-limited update; no insert or delete for `authenticated`. Checked by `supabase/tests/notion_outbox.sql`.

## Decisions for approval (defaults taken)
1. No new dependencies (`after()` is in Next 16). 2. Schema as above. 3. Same transaction by trigger. 4. No stored payload. 5. Six statuses. 6. Setup row only if REQ-33 is on `main` (it is not). 7. Keep the `schedule_summaries` columns. 8. Three workers: the save, `withBackgroundDrain`, the hourly run. 9. 30 s doubling to 1 h, 8 attempts, 350 ms spacing, 10 rows or 20 s, stale after 10 minutes. 10. Every class change enqueues the org's daily task. 11. "Sync all" goes through the outbox; Create now stays direct and can be `uncertain`; notice Retry moves to `/exports/retry`. 12. Retry with a pending sibling supersedes and drains the pending row. 13. Next free ADR number. 14. The feature PR carries `needs-human-merge`.

## Out of scope
A queue service; people sync (REQ-38); billing writes; automatic recovery of an uncertain append; dropping `schedule_summaries` columns; outbox rows for availability changes; pruning old `done` rows.
