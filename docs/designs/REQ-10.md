# Design: REQ-10: Upgrade Next.js to 16.3.8 in both apps

Copied from the approved Notion card: https://app.notion.com/p/3f9d6ae73dd781e18283c7597d199734

**Summary:** Move every `next` and `eslint-config-next` pin in the workspace (landing, tracker and `packages/db`) from 16.1.6 to 16.3.8. This clears the 2 critical and 24 high Next advisories with no change in behaviour for students, tutors or parents.

**Risk:** High. There is no migration and no new package. It upgrades the framework underneath both auth gates: the `apps/landing/middleware.ts` session refresh and the `apps/tracker/proxy.ts` sign-in redirect. Every changed manifest and the lockfile is in `human_merge_paths`, so the PR gets `needs-human-merge`.

## Problem

`pnpm audit --prod` on 2026-10-14 flags `next@16.1.6`, including proxy and middleware bypasses that matter for the tracker's signed-out redirect. `packages/db/package.json` also pins `next` 16.1.6, as both a peer and a dev dependency, so it must move with the apps.

## Acceptance criteria

- AC1: `apps/landing`, `apps/tracker` and `packages/db` (peer and dev) all pin `next` to exactly `16.3.8`. Both apps pin `eslint-config-next` to exactly `16.3.8`. No other `package.json` entry changes.
- AC2: `pnpm-lock.yaml` is regenerated by `pnpm install` at the root and has no `next@16.1.6` or `@next/*@16.1.6` entry. `pnpm install --frozen-lockfile` succeeds.
- AC3: `pnpm audit --prod` reports no critical or high advisory on `next`. Every advisory still open is listed in the PR body with its severity, path and fixed version.
- AC4: All `gate_commands` pass, and both apps build.
- AC5: `pnpm test:rls`, `pnpm test:sso` and `pnpm test:tracker` pass, with no assertion removed or loosened.
- AC6: A signed-out tracker request through the landing proxy still redirects to `/login?next=<path>` (SSO checks 2, 5c and 7). A prefetch still skips the proxy (check 7b). `/api/scheduler/daily-task/run` still answers 401 without its secret.
- AC7: The PR body has a "Next 16.1.6 to 16.3.8: proxy and middleware changes" section.

## Approach

Bump the three manifests, regenerate the lockfile, then run the audit, gates, builds and e2e suites. If a test fails, fix the code to match the new Next behaviour, never the assertion. Out of scope: Next 16.4 or 17, React, other dependencies, renaming landing's `middleware.ts` to `proxy.ts`, security headers (REQ-11) and Dependabot (REQ-12).

## Build note (approved by the owner on 2026-10-15)

Next 16.3 answers an RSC request that is missing a valid `_rsc` cache-busting parameter with a 307 to the same URL plus the correct `_rsc`. This is cache-poisoning protection in `next/dist/server/base-server.js`. SSO check 7b sent a bare prefetch with no `_rsc`, so it saw that 307 and failed, even though the proxy matcher still skips prefetches.

With the owner's approval, the check now follows only that same-path `_rsc` hop. Its assertion is unchanged: the response must not be a redirect. A proxy redirect to `/login` is never followed, so the check still fails if the proxy runs on a prefetch.
